### 5. 创建 SoftAP 与关键硬件限制
- **hostapd 残留**是 Wi-Fi 无法连接的根本原因（PID 25228 占用资源，阻止 wpa_supplicant 启动）
- 清理 hostapd 后，**0041 模块下 Wi-Fi 可正常连接**
- `cmd wifi start-softap` 在 wificond 重启后可成功创建 `wlan2` (AP)
- **致命限制：AP + monitor 不能共存**：
  - 有 monitor 时 SoftAP 第一阶段（接口创建）失败
  - 删除所有其他接口（wlan0/p2p0/wifi-aware0），只保留 AP，monitor 仍然无法创建
  - `iw phy phy3 interface add awdlmon type monitor` → `Invalid argument (-22)`
  - 并发限制中**没有任何组合允许 AP + monitor 共存**
  - 这是固件层面的硬性限制，无法绕过

### 6. P2P GO 同样受限
- `iw list` 显示支持 `P2P-client` 但不支持独立的 `P2P-GO` 接口模式
- `valid interface combinations` 中有 P2P-GO 条目，但 `Supported interface modes` 中没有
- P2P GO 在 Android 上通过 `type managed` + wpa_supplicant P2P 功能实现，但 wpa_supplicant 控制接口被框架独占

## 当前结论

### TX 层面
**固件结构性拒绝 host-built 数据帧通过 exception path。**

| vdev 类型 | 负控制帧 | well-formed 帧 | 固件反应 |
|-----------|---------|---------------|---------|
| monitor (0037-0039) | rejected | 提交后 RDDM | `cmnos_thread_patch.c:1170` |
| STA (0040-0041) | rejected | 提交后**重启** | 同地址崩溃 |
| p2p0 | rejected | rejected | 驱动拒绝，未达固件 |
| AP | 无法测试 | **无法测试** | AP + monitor 不能共存 |

0038/0039 已穷尽可能性：exception-frame 契约 + 完整 TX 参数，固件崩溃 PC **一字未变**——它拒绝的是"host-built 帧"这个概念本身。

### 硬件限制
**AP/P2P-GO 与 monitor 不能共存。** 这意味着方向 1（AP carrier + monitor RX）在单网卡架构下**不可行**。

## 剩余可行方向

1. **双路径架构**（大改）：
   - RX 不走 monitor，走 **mission 共享环**（0027 已验证，STA 关联时可收 AWDL Action）
   - TX 走 **AP 接口**（SoftAP 已验证可创建）
   - 需要移除 monitor 依赖，改驱动在 AP 接口上支持 raw injection

2. **外接 USB 网卡**（ROADMAP 兜底）：
   - 已验证 carl9170 支持 monitor+inject
   - 手机自带 Wi-Fi 完全不动，AWDL 射频走外置网卡
   - 体验差（要插东西），但功能可用

3. **放弃 raw injection，走正常数据路径**：
   - 通过 socket 发送，让协议栈生成正确的 802.11 帧
   - 但 AWDL 帧格式特殊（SNAP、BSSID 等），正常路径无法生成
   - 需要 filin 协议栈适配，工作量大

## 6. 社区研究重大发现

### QCACLD-2 的成功注入路径（Codeaurora commit 3d3ad78，2016-11）

**完全不同于我们的 exception path**：
- **TX 入口**：`hdd_hard_start_xmit` → `tlshim` → `ol_tx_hl_base()`（**HL path**，不是 exception）
- **固件契约**：radiotap 头作为 **extra DMA fragment** 传给固件，固件自己解析 `it_present`  bitmap 获取 rate/retries
- **peer 处理**：使用 `tlshim_selfpeer_vdev()`（self peer），跳过正常 STA lookup
- **编译依赖**：需要 `CONFIG_HL_SUPPORT`
- **关键代码**：`adf_nbuf_frag_push_head(msdu, rtap_len, rtap, 0, 0)` + `adf_nbuf_set_frag_is_wordstream(msdu, 1, 1)`

### QCACLD-3 的现状（社区确认）

- **`wlan_mon_drv_ops` 没有 `ndo_start_xmit`**（CSDN 博客 `shalan88` 确认）
- **monitor / pktcapture 模式只提供 open/stop/stats**，不支持 TX
- **正常 TX 路径**：`hdd_hard_start_xmit` → `ucfg_dp_start_xmit`（DP 架构，HL path 已不存在）
- **Qualcomm 在 QCACLD-3 中有意移除了 monitor 注入能力**（kimocoder 项目确认 "propably deactivated by Qualcomm"）
- **QCACLD-3 的 `pkt_capture` 子系统**（CAF tag `wlan-cld3.driver.lnx.2.0.r60-rel`）有 radiotap iterator 代码，但当前只用于**捕获**，不用于注入

### 关键对比

| 维度 | QCACLD-2（成功） | QCACLD-3（我们的尝试） |
|------|-----------------|---------------------|
| TX 路径 | HL path (`ol_tx_hl_base`) | Exception path (`cdp_tx_send_exc`) |
| 接口 | monitor 有 `ndo_start_xmit` | monitor **无** `ndo_start_xmit` |
| 固件契约 | radiotap as extra fragment | `is_tx_sniffer` + ext2 header |
| 固件行为 | 解析 radiotap，正常发送 | 同一 PC 断言崩溃 |
| 固件版本 | 旧固件（支持 HL） | kiwi_v2 固件（DP 架构） |

### 根本差异

我们的方法（0037-0041）**在重建一个不存在的路径**：
- 0037 手动创建 monitor vdev 的 TX descriptor pool（HL 时代固件自动做的）
- 0038/0039 手动构造 exception-frame 契约和 TX 参数（HL 时代固件从 radiotap 解析的）
- 结果：固件在 `cmnos_thread_patch.c:1170` 崩溃，PC 不随参数变化 → **固件拒绝的是路径本身**

### 剩余可行方向（更新）

1. **在 QCACLD-3 中恢复 HL path 或等价的正常 TX 路径给 monitor**
   - 在 `wlan_mon_drv_ops` 中添加 `ndo_start_xmit`（像 QCACLD-2 那样）
   - 但需要适配 DP 架构（`ucfg_dp_start_xmit` 而非 `ol_tx_hl_base`）
   - monitor vdev 没有 peer/self-peer，DP 路径可能需要特殊处理
   - 大改，但可能比穷举 exception path 参数更有前途

2. **尝试保留 radiotap 头作为 extra fragment 走 exception path**
   - 当前 `hdd_mon_awdl_start_xmit` 剥离了 radiotap（`skb_pull(skb, 13)`）
   - 也许固件期望看到 radiotap fragment？
   - 但 QCACLD-3 的 `cdp_tx_send_exc` 是否支持 fragment 格式未知

3. **使用 `pkt_capture` 子系统的 TX 能力**
   - CAF tag `wlan-cld3.driver.lnx.2.0.r60-rel` 有 radiotap 解析代码
   - 但当前只用于 RX capture，TX 侧未开源或未激活

4. **外接 USB 网卡**（最可行）
   - carl9170 已验证支持 monitor+inject
   - 绕过 QCACLD-3 所有限制

## 15:00-15:20 — AWDL 帧格式统一到 filin-rs，首次被 Mac 的 awdl0 ACK

## 15:45-16:10 — RX 定论：受支持路径收不到 AWDL 帧

用户反馈 AirDrop 面板看不到设备。判断：面板需要 RX（同步+mDNS+发现），TX 的 ACK
不构成发现。转去查 RX。

**主机侧的门是开的（之前的 -22 是我自己的 bug）**
- `NL80211_ATTR_FRAME_MATCH` 在本内核**强制**：`nl80211_register_mgmt()` 首句
  `if (!info->attrs[FRAME_MATCH]) return -EINVAL;` → 不带就 -22，看着像驱动限制。
- `wlan_hdd_txrx_stypes[STATION].rx` 本来就含 `BIT(SIR_MAC_MGMT_ACTION=0xD=13)`。
- 目标内核常量：`ATTR_FRAME_TYPE=101`（不是 52）、`CMD_REGISTER_FRAME=58`、
  `CMD_REMAIN_ON_CHANNEL=55`、`ATTR_FRAME_MATCH=91`。

**阳性对照（关键）**：`--rx-ms 2000 --type 0x0040 --match-hex 00` 在 2437 上
收到 **11 个 probe request**，帧体完整。→ 注册/ROC/cfg80211 交付/mlme 组全正常。

**AWDL 帧稳定为 0**：6 字节 match `7f0017f20810`，注册返回 0、ROC 返回 0，
2437 三轮 + 5745 两轮全部 `rx_frames=0`。同一信道同一时刻 Mac 能 ACK 我们的单播
数据帧，我们收不到它的广播 action 帧。

**结论**：固件 STA 模式按地址/BSS 过滤 RX，未知 BSSID（`00:25:00:ff:94:73`）的
广播 action 帧在 RX filter 就被丢，不产生 WMI 事件。唯一能收 AWDL 的是
global monitor（con_mode=5），与普通 Wi-Fi 互斥。**这是端到端的真正阻塞点。**

**更正旧结论**：§9.3 说 wiphy 没有 `WIPHY_FLAG_OFFCHAN_TX` 是错的，
`wlan_hdd_cfg80211.c:18490` 无条件置位。但实测确认 freq 参数仍被忽略：
不 ROC 打 2437 → 0/20 ACK；加 ROC → 2/20 ACK。**ROC 仍然必须**，只是原因不是缺 flag。

**新增工具能力**（`tools/awdl-mgmt-tx.c`）：`--rx-ms N [--type hex] [--match-hex hex]`
自注册 action/probe 帧 + 自持 ROC + 打印收到的帧；`--plan` 增加 `elapsed_us` /
`FELL_BEHIND` 报告（每帧 netlink 开销约 16.7ms，2s 窗口最多 ~120 帧）。

## 16:20-16:45 — RX 打通：保持关联的占空比捕获（推翻 §11）

**结论：RX 不是死路。** §11 只测了 cfg80211 `REGISTER_FRAME`（wlan0+ROC）那条路；
0021/0027 的 **monitor vdev 共享环 raw RX** 一直在代码里，只是转攻 TX 后没再跑过。

操作：`iw phy phy3 interface add awdlmon type monitor` → `ip link set awdlmon up`
（内核日志 `MARIONETTE_STA_MONITOR_INIT_RESULT ret=0`、
`MARIONETTE_MONITOR_RAW_RX vdev=N`）→ 写
`/sys/module/kiwi_v2/parameters/marionette_awdl_capture_ms`。

**参数格式是 `<频率MHz>:<毫秒>`**（只收 2437/5220/5745，1..200ms）。写 `6:200` 会
被当非法频率返回 -EINVAL，`echo` 只报 1，极像权限问题 —— 踩过一次。

结果：
- 满占空比（无间隔）→ 10 秒后 BEACON MISS 掉线（`policy_mgr` 没登记 monitor vdev，
  不会给 STA 让 beacon）。
- **200ms 时隙 + 400ms 间隔** → 12 秒收 **86 个 AWDL action 帧**（8 个设备，含本机
  Mac 02:57:dc:2d:32:26），**STA 全程关联，ping 6/6 0% 丢包 avg 11ms**。
  这是第一个「Wi-Fi 无感 + 稳定收 AWDL」的工作点。

**真实线上格式（修正 filin-rs）**：TLV 从帧偏移 **40** 开始（按 39 解析出垃圾）。
真实 TLV 序列 PSF=`[4,5,18,19,6,24,12,7,17,21,33]`，MIF=`[4,5,18,24,12,7,17,16,21,6,2×9]`。
我们 `build_announce_tlvs` 把 **5 和 18 的语义搞反**（真实 5=sync tree 带 master 地址，
18=election params），且缺 19/17/33、TLV 4 实际 73 字节。MIF 的 **TLV 2 是服务描述**
（`sn=com.apple.sharingd.AirDrop`、`sid=`、`dmn=刘强强 Mac Pro`、`flags=111611`）——
这才是 Mac 能不能看见我们的判据。

**约束**：`awdlmon` 存在时 Wi-Fi 无法重新关联，`iw dev awdlmon del` 后立刻恢复。
常驻服务必须按连接状态管理它的生命周期。

证据：`build/airdrop/driver/coexist-rx/frames-2026-10-21.log`（45 个完整帧）；
ROADMAP §12。

## 17:10-18:10 — TX 卡点拆成三个缺陷，机制改为「滤镜/信道分离」

**目标切换**：用户要求"实现完整 airdrop 服务"，RX→TX→发现 三段都要通。

**ROC 不是解法（实测）**：`roc_start(2437,2000)` 期间并发 ping 网关，**0% 丢包**，
但 seq 4/5 时延 14ms→52/48.8ms 正好在窗口内。结论：policy manager 把 ROC 实现为
与 STA 的**时间片共享**，会按时回主信道取信标。它保链路，但永远停不住电台。

**捕获槽的真实代价**：走 `wlan_hdd_set_mon_chan` 直接改 monitor vdev 信道，
policy manager 不知情 → 信标看门狗照常计时 → 约 10 个连续丢信标（≈1s）就
`BEACON_MISS_FAILURE` 断连。**断连后所有 TX 返回 -107 ENOTCONN**，极易误判成注入失败。
且每槽额外约 **280ms** 换信道开销（6 个 200ms 槽在 600ms 循环里落在 870–910ms 间隔），
所以"短驻留+长间隔"根本排不出来。

**关键设计结论**：三个缺陷同源——把"装滤镜"和"移信道"绑在一起。
- 滤镜必须驱动内部做（`marionette_capture_phase`，monitor 全套 RX 滤镜只在此相位生效）；
- 移信道必须走 policy manager 认可的路径（STA 的 ROC）。
补丁 **0045 `marionette_awdl_capture_hold`** 把两者拆开：参数只切滤镜不碰信道。

**排除的假设**：
- `pkt_capture`：kiwi_v2 未编译该特性，模块里无 `packet_capture_mode`。
- 钉在 5220 白拿社会信道：`LIMO-5G ceshi` 确实在 5220 有 BSS，但实测三信道流量
  **2437:11 / 5220:0 / 5745:16**，本地 Apple 设备不用 5220。不成立。
- 建 `awdlmon` 会打断关联：实测建后 4s 内每 400ms 采样始终 Connected。是槽打断的。
- 不写槽也能收帧：不写槽 `CAPTURE_SUMMARY total=0`，滤镜相位才是 RX 开关。

**自己发的帧收不到**：60 个 AWDL 帧、15 个发送者里 `our_tx_seen=0`。monitor 不回环
自身发射，所以判据只能是 Apple 设备开始向我们单播（`frames_addressed_to_us`）。

**新增工具**：
- `native/airdrop/tools/awdl-stack-load.sh` — 设备重启后重载 marionette 栈（load/stock/status）。
- `native/airdrop/tools/awdl-tx-in-slot.sh` — 槽内发射（已证明会被信标超时杀死）。
- `native/airdrop/tools/awdl-roc-tx.sh` — 滤镜保持 + ROC 内发射（0045 的验证脚本）。
- `marionette-awdl-mgmt-tx` 的 ROC 改为 **默认关闭、`--roc` 显式开启**，避免与槽打架。

**构建**：`colima ssh -p ohos-arm -- bash -lc '...'`（必须 `bash -lc`，直接传命令会被当文件名）；
make 变量见 `native/airdrop/driver/build-baseline.sh`，漏 `MODNAME=kiwi_v2` 会走内核内建分支报错。
全量重编约 35–40 分钟，LTO 链接单线程是瓶颈。

证据：ROADMAP §13。

## 18:10-18:40 — TX 打通：Apple 设备开始 ACK（含两处重大误判更正）

**更正上文两条错误结论**：
1. **`-107 ENOTCONN` 与掉线无关**。它来自 cfg80211 的 AWDL 放行开关
   `/sys/module/cfg80211/parameters/marionette_awdl_mgmt_tx`（默认 **N**）。
   关着时链路完好也返回 `-107`；置 Y 后立刻 `0`。`awdl-stack-load.sh` 必须打开它。
   同时 DATA 帧还要 `marionette_awdl_data_tx=Y`（0043/0044）。
2. **`roc_failed` 不是 ROC 不可用**。monitor 存在时 ROC 上限从 2000ms 掉到
   **正好 200ms**（250 就 -22），且对 STA 主信道 ROC 必失败。改用 200ms 切片链后
   `roc_rearms=7 / roc_failed=0`。

**最终生效的机制（coexistence-safe）**：
```
echo 1 > .../marionette_awdl_capture_hold     # 0045：只开滤镜，不碰信道
marionette-awdl-mgmt-tx wlan0 2437 1 --plan <plan> --roc   # 200ms ROC 链 + 发射
echo 0 > .../marionette_awdl_capture_hold
```
实测一轮 1.5s / 28 帧：`submitted=28 rejected=0 roc_rearms=7 roc_failed=0`，
捕获 **72 个 AWDL 帧全部 freq=2437**，链路末尾仍 Connected。
（对比旧的槽方案：8 帧全在 5260，且 1–2 秒必掉线。）

**决定性证据**：发给 Mac AWDL 地址 `02:57:dc:2d:32:26` 的单播 DATA 探针出现
`DATA off=105000 len=88 cookie=257 ACKED`。四轮重复 `1/1/1/0`，合计 **4/16≈25%**，
与 AWDL 可用窗口占空比吻合。**TX 链路层已打通**。

**仍未做到**：对端不向我们单播（`frames_addressed_to_us=0`），即还没被接受为同步源。
下一步要按对端可用窗口对齐发射时机，而不是均匀撒点。

**补丁 0045** `marionette_awdl_capture_hold`：只切 `marionette_capture_phase` 并
`marionette_monitor_refresh_filters`，不碰信道。补丁文件
`native/airdrop/driver/0045-capture-hold-without-channel-move.patch`。
模块 24MB（`llvm-strip --strip-debug`），sha256 `49bc74fa…`。

证据：ROADMAP §14。

### 20:40–21:00 MIF 服务记录结构定案；推翻 §16.3 两条结论

**设备访问路径变了**：`colima ssh -p ohos-arm` 落到的是纯 Linux 构建 VM，
没有 adb / iw / svc。真机走宿主机的 adb：
`/Users/lin/Library/Android/sdk/platform-tools/adb -s 510af65c shell 'su -c "..."'`
（2211133C / fuxi）。工具都已在 `/data/local/tmp/`。

**纠正一：所谓"模板 TXT 串被截断 2 字节"不是缺陷。**
把 coexist-rx/frames-2026-10-21.log 里 9 帧 MIF（8 个不同 Apple 设备）全量比对：
每个 TLV 2 payload 末尾都固定有 2 字节，且正好是最后一条记录少的字节
（`ok`/`op`/`2)`/`ro`）。即**最后一条记录声明的 L 比真实 body 短 2**，
这是线格式约定。awdl-identity.py 把尾部并回最后一条记录再重写、发回时切回去，
用模板自身身份回写可逐字节复原（`--selftest`，8/8 真实帧通过）。

**纠正二：没有"9 字节二进制主机 id"。**
`e784b1e69e97e79a84` 是 UTF-8 "焱林的" 的前 9 字节，主机名就是 `焱林的MacBook`。
DNS 标签同形，主机名标签只能靠"紧挨在 `_appsvcprepair` /
`_applicationservicepairing` 前面"定位；按 ASCII/非 ASCII 挑标签会把服务名
误判成主机名（宿主 `ionservicepairing`），这就是旧版改写落空的原因。

**新发现：第二处身份泄漏。** SRV rdata 尾部的 36 字符 UUID 与 TLV 16 的
ARPA 名逐字节相同（8/8 帧验证）。Rust 的 `announce_template.rs` 只改 TLV 16，
SRV rdata 里一直是 Mac 的 `b4fb8f9f-5a19-485b-86d4-1b497dc19d38`。

**另一坑**：TLV 2 里还有非 AirDrop 服务（裸压缩指针 name + 12 字节标签
`d0550ba77089`、TXT `flags=1116`），必须按服务名标签门控跳过，
否则会被误改成长主机名导致帧长 +13。

**我们的身份**：host=marionette / display=Marionette /
sid=2C9D473F-65EB-4AB7-82C7-757E4B8D06B9 / at=4656d6de6b8a /
uuid=8DD0D393-ABA1-4727-B338-75B9F049A66A（TLV16 与 SRV rdata 一致）。
改写后 14 帧 MIF：Mac 5 个身份串全为 0，我们的 5 个全 14/14，TLV 序列不变。

证据：ROADMAP §17；`native/airdrop/tools/awdl-identity.py --selftest`。

## 修掉 §14.5 的 blocker：可用窗口 epoch 跨突发连续

`awdl-emit` 的 `base_us` 硬编码 0 → `phy_tx` 恒为 0、`aw_counter` 每轮从 0 重来，
对端看到"时间倒流"就不会记录我们。新增 `--epoch-us` / `--epoch-now` / `--lead-us`：
内容按 `base+rel` 盖戳，偏移按 `lead+rel` 排，`--epoch-now` = `now+lead`（进程内读
CLOCK_MONOTONIC，与 daemon 同一时钟）。`runtime::host_time_us` 改 pub。抽出
`resolve_epoch` / `build_plan` 以便测试。`awdl-beacon.sh` 改为每轮重建 plan。

设备实测：旧行为两轮都是 `phy_tx=00000000 aw_counter=0000`；新行为 1.17s 内
`aw_counter` 14482→14554（+72 ≈ 71.7 个 16TU 窗口）。**关键教训：宿主 `cargo test`
对 filin-rs 从来无效**（Linux 常量 + `sockaddr.sa_len`），正确做法是
`cargo test --target aarch64-linux-android --no-run`，把测试二进制推到
`/data/local/tmp` 直接跑 —— 本轮 filin_rs 242 passed / awdl_emit 6 passed 都是这么来的。

**现场纠错**：`radio.sh` 用磁盘 .ko 的 sha256 判断能力是假阴性 —— 文件是原厂
（marionette 计数 0），但已加载模块有 35 个 `marionette_*` 参数
（data_tx=Y / sta_monitor=Y / raw_tx=N）。且 `radio.sh` 走的 con_mode=4 全局监听
与 §14.3 验证过的"关联+awdlmon+capture_hold+ROC+mgmt_tx"不是同一套。

另：`iw scan` 在本机 iw 上是非法子命令，会打印 usage，usage 里有 "BSS" 字样，
`grep -c BSS` 会得到 8 这种假读数，必须用 `iw dev wlan0 scan`。

证据：ROADMAP §19。
