## AirDrop 驱动：监视 vdev 路径重新打通（0045），随后设备离线

### 关键认知修正

**之前几次"监视抓包 0 帧"是假阴性**：那些 pcap 只有 24 字节（纯文件头，零包）。
唯一有效的监视抓包是 10-22 08:48 那次（25.5 MB / 86 619 帧 / 5260 MHz）。
所以"没有对端在射程内"这一结论从未被真正建立过——不能拿空 pcap 当阴性证据。

**stock 驱动不能建监视 vdev 的结论已撤回**：当时的 `-22` 是 wiphy 尚未注册（驱动刚
insmod，`iw dev` 为空）。不是"stock 不支持 monitor"。

**candidate-0046 拒绝建监视 vdev 的真实原因**：dmesg
`__wlan_hdd_add_virtual_intf: Adding monitor interface not supported`。
monitor-while-associated 的能力正是补丁 0009 提供的；10-22 的修复把
`marionette_awdl_sta_monitor=1` 关掉，等于同时关掉了这条路径。这是"修关联回归"
换来的代价，必须显式记账。

### 突破：0045 + sta_monitor=1 能建监视 vdev 并真的收到帧

`/data/local/tmp/marionette-candidate-0045.ko` 仍在设备上。用它加载
（`sta_monitor=1`）后：基站能钉在 channel 44，监视 vdev 创建成功，
tcpdump 抓到 **7673 包**——监视 RX 路径是活的。

**重要保留**：该监视 vdev 起来时在 **2422 MHz**（脚本没设信道），不是 5220，
所以这 7673 包几乎肯定只是 2.4G 的 beacon，**不能**据此说收到过 AWDL 帧。
它只证明"监视 vdev 能向主机交付帧"。

随后 STA 链路掉了。`iw dev awdlmon set channel 44` 被拒（`-16`，EBUSY），
紧接着手机重启。这次重启属于 ROADMAP §21.4 的同类崩溃，**下次复现前必须先
`insmod marionette_die_logger.ko`**，否则又拿不到现场。

### 补丁 0018 的时隙语法（已核对源码）

`marionette_awdl_capture_ms` 接受 `<freq>:<duration_ms>`，例如 `5220:200`
（**频率在前**）。patch 0015 的纯时长模式只允许 1–200 ms，写 30000 会 `-EINVAL`。
patch 0018 在捕获阶段放宽 0009 的信道检查，所以 STA 可以留在原信道、监视端
短暂跳到 5220 —— 这才是"不破坏关联地看 44"的正解，比 `set channel` 安全。

## 结果：AWDL 接收成立（10:33–10:41）

上面第 6 步的答案是**有**。手机重连后按顺序跑通：

- 残留的 `awdlmon` 接口是关联失败的元凶——**必须先删掉监视接口再关联基站**，
  否则补丁 0009 把 STA 可用信道锁到监视 vdev 的信道，连不上任何 AP。
- 基站关联到 `70:3a:73:a2:26:68`（5260 / −42）后建 `awdlmon`（**不设信道，跟随基站**），
  立刻 tcpdump，抓到真实 AWDL。

| 运行 | 时长 | 总包 | AWDL 帧 | Δmon_post_awdl |
|---|---|---|---|---|
| run1 | 20s | 56 314 | 32（PSF 3 + MIF 29） | +32 |
| run2 | 25s | 6 625 | 9 | +9 |

pcap 帧数与驱动计数逐次相等 → 计数可信。帧：addr1 广播、addr3 `00:25:00:ff:94:73`、
前缀 `7f 00 17 f2 08 10`、长 328–1079 B。

**两个改变方向的推论**：

1. **不需要跳台到 44。** Mac 的 AWDL 同时在信道 6（2437）和 AP 信道 52（5260）上。
   手机与 Mac 同 AP 时，监视端跟随基站信道就能收到。此前"44 上 0 帧"的根因是
   **对端不在 44 上**，不是固件丢帧。
2. **`awdl_rx_wmi=0` 不是故障。** 它在 STA/mgmt 路径；AWDL 广播走监视 vdev 的
   direct-buffer 路径，由 `mon_post_awdl` / `mon_desc_total` 统计。此前把它当唯一
   判据是这条弯路的主因。

**新障碍**：共存不稳定——监视 vdev 建后 20–40 s 被驱动拆除、基站同时掉线；
删 vdev 后基站 1 s 恢复。补丁 0009 的实验性做法要换掉。这是"常驻"的第一障碍。

**仍未验证**：发送、双向发现、IPv6 数据通道、文件互传。

**新增文件**：
- `build/airdrop/driver/awdl-rx-20261023/`（41 帧完整字节 + README）
- `native/airdrop/tools/pcap-awdl-analyze.py`（pcap → AWDL 帧分类器）
- ROADMAP §25、`docs/AIRDROP.md` 检查点已更新

**踩坑记录**：`iw phy phy0 interface add ... type monitor` 常打印
`command failed: Invalid argument (-22)` 但**接口实际已创建**，必须用 `iw dev` 判断；
`tcpdump` 若接口中途被拆会给出 `0 packets captured` + 24 字节 pcap，这不是阴性结果。

## 两个新发现的坑

- **0051**：sink radiotap 只有 CHANNEL，filin 的 `tsft_offset_us=0`、
  `synced=false`、`aw_alignment_pct=0`，可用性窗口无法对齐。把
  `mon_pdev->ppdu_info.rx_status.tsft` 经 `marionette_monitor_post_frame(frame,len,tsft)`
  传进 sink，radiotap 变 24 字节（TSFT|CHANNEL，TSFT 在 offset 8）。
- **0052（重要）**：`awdlsink` 是懒创建、只在 `marionette_awdl_sink_exit()` 销毁。
  模块重载时旧 netdev 常常残留，新实例 `register_netdevice` 恒 `-EEXIST`，
  `marionette_sink_dev` 一直是 NULL → **所有帧进 sink_drop**，表现和"附近没有对端"
  一模一样（tcpdump 能绑上、抓不到包）。实测 `post_awdl=288 / sink_rx=0 /
  sink_drop=288`，dmesg 反复 `MARIONETTE_AWDL_SINK_UP_FAILED ret=-17`。
  修复：创建前用 `dev_get_by_name(&init_net, name)` 找回残留 dev 并
  `unregister_netdevice()`（不能复用，ops 指向已释放的旧模块镜像）。
- 教训：**`sink_rx` 必须和 `post_awdl` 一起看**，只看 awdl 计数会以为接收正常。
